技术栈：用什么写的，为什么

一句话总结：Swift 6 + SwiftUI/AppKit 混合 UI 的 Swift Package 项目，仅一个运行时三方依赖（Sparkle），其余全部压在 macOS 系统框架上；另有两条"重资产"支线——DDC 私有 API 与自编译 libimobiledevice。

本页目录 语言与工具链 包结构（SPM targets） UI 框架策略：SwiftUI + AppKit 混合 系统框架全景（按用途） 第三方依赖 两条重资产支线 构建 / CI / 发布链 测试体系 对复刻项目的技术选型建议

包结构（SPM targets）

Package.swift
├── StatusTrio          (executable)  入口：main.swift → NSApplication → AppDelegate
├── StatusTrioCore      (library)     全部业务：监控/状态/渲染/UI/设置/本地化/遥测
│   └── Resources/                    12 个 .lproj（Localizable.strings + InfoPlist.strings）

UI 框架策略：SwiftUI + AppKit 混合

统计全部 import：SwiftUI 54 处、AppKit 55 处——两者几乎对半，分工明确：

层框架典型职责
菜单栏 / 状态项AppKitNSStatusItem、自绘 NSImage、NSPopover 锚定、右键菜单、激活策略切换、Dock 图标
弹层 / 设置内容SwiftUIStatusPopoverView、设置中心各 Section、引导页、设备列表行
图标渲染CoreGraphics（AppKit 内）120×120 几何坐标系手绘环形/符号/点位，非 SwiftUI 绘制（性能与像素控制）
动画QuartzCore + 自研时钟充电动画走 ChargingEffectClock（时间线/相位/帧缓存），菜单栏侧用 layer presenter
这种"AppKit 管壳（状态栏/弹层/生命周期），SwiftUI 管内容"的混合是 macOS 菜单栏工具的主流成熟做法——NSStatusItem 与新弹层玻璃效果在纯 SwiftUI 里都拿不到完整控制权。

两条重资产支线（技术风险点）

① DDC / CI 显示器控制 私有 API

DDCPrivateAPI 是一个 C 头文件 target，声明了 IOKit 中未公开的三个符号：

extern IOAVService IOAVServiceCreateWithService(...);
extern IOReturn IOAVServiceReadI2C(...);   // 读显示器 DDC 寄存器
extern IOReturn IOAVServiceWriteI2C(...);  // 写显示器 DDC 寄存器

用于直接控制外接显示器的硬件音量。风险：私有符号随时可能在系统版本中变化；不同显示器 DDC 实现参差（项目用 DDCVolumeReply 处理回复时序）。

② libimobiledevice Helper 第三方协议

绕开 Apple 官方接口、直接说 usbmuxd 协议读 USB 设备。风险：协议随 iOS 版本演进（依赖锁定 commit，升级需重验）；构建链路长（6 个库按序构建 + RPATH/依赖检查脚本）。

复刻决策参考：这两条支线是 Status Trio 的差异化卖点，但都是"非公开契约"。若复刻项目要上 Mac App Store，DDC 私有 API 与未沙盒的 Helper 都不可行；走 Developer ID 自分发则可行但需自担维护成本。

关键工程决策：

  • CI 即验收环境：AGENTS.md 规定任何触碰 actor 隔离 / SwiftUI 绑定 / Bundle.module 的改动，合并前必须跑一次不发布的 release workflow 预检；
  • 失败即记录：每次 CI 失败必须登记进 docs/swift-ci-compatibility.md（run ID、根因、修复、验证）——相当于公开的事故账本；
  • 27 个脚本几乎都是"契约测试"：SDK 版本、Sparkle 元数据、appcast 最低系统版本、helper 的 RPATH 与依赖完整性等，把"容易静默坏掉的东西"变成可执行断言。
