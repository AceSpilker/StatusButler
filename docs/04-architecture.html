04 / Architecture

架构与数据流：4 万行如何组织

单进程、单组合根、四层单向依赖的 MVVM 变体：监控层协议化读系统 → 状态仓库聚合 → 展示映射层把状态翻译成"场景" → UI 层渲染。全 Swift 6 严格并发，核心对象 @MainActor。

本页目录 启动链路与组合根 四层架构与目录映射 核心数据流：事件驱动 + 兜底轮询 StatusSnapshot：一个值类型统治图标 图标渲染管线 蓝牙电量：三源合并 + 可见性门控 设置系统与响应式联动 遥测与生命周期 可复用的架构经验

启动链路与组合根

main.swift                      // 7 行：NSApplication + delegate + run()
  └─ AppDelegate (applicationDidFinishLaunching)
       ├─ SingleInstanceGuard()          // 失败即 terminate（单实例锁）
       └─ AppEnvironment.live()          // ★ 组合根：一次性装配全部依赖
            ├─ SettingsStore()               // UserDefaults → 60 个 @Published
            ├─ makeStore(…)                  // SystemStatusStore + 7 个监控器
            │     └─ BluetoothDeviceController(三源电量注入)
            ├─ Localization()                // 12 语言
            ├─ IconPresentationViewModel     // 状态 → 图标场景
            ├─ StatusBarController           // 菜单栏图标 + Popover
            ├─ AppIconController             // Dock 图标 + 激活策略
            ├─ SettingsWindowController / OnboardingWindowController
            ├─ MainMenuController            // 常规应用菜单
            ├─ ChargingEffectClock / MotionMonitor
            └─ TelemetryReporter
       environment.start()             // 顺序启动各子系统（store 最后）
  UpdaterManager.start()               // Sparkle

AppEnvironment 是教科书式的手工依赖注入容器：所有生产对象在 live() 里构造、闭包串联（如 Dock 渲染回调直接注入 DockIconRenderer.image），测试可按需替换任何一环。AppDelegate 本身只有 93 行——逻辑全部在组合根。

四层架构与目录映射

① Monitoring 监控层 · Monitoring/ 37 文件
每个系统信号一个监控器，全部面向协议（MonitorProtocols.swift）：BatteryMonitor / WiFiMonitor / NetworkConnectionMonitor / VPNMonitor / VolumeMonitor / AudioInputMonitor / BluetoothDeviceController / MobileBatteryController / AppleDeviceDiscoveryController… 另有 ReadWatchdog（读超时看门狗）、SystemEventObserverBag（通知注销聚合）等基建。
▲ 只产出状态值，不知道 UI 存在
② Store 状态仓库层 · Store/SystemStatusStore.swift 1043 行 + Models/ 38 文件
@MainActor ObservableObject。聚合所有监控器为单一 StatusSnapshot（+ 弹层专用 popupSnapshot、vpnStatus 等旁路状态）；持有子控制器（电池详情 / Wi-Fi 网络 / 主链路 / 蓝牙设备 / 移动电池 / Apple 设备发现 / 聆听模式）。Models 层全是不含行为的值类型（快照、选项、目录）。
▲ 只做"状态→表现"的纯映射，无系统调用
③ Presentation 展示映射层 · Presentation/（Icon 9 文件 + Panel 11 文件）
两套映射器：图标侧 IconPresentationMapper 把快照+外观配置翻译成 IconSceneState（外环/中心/底部三段场景）；面板侧 PanelPresentationMapper 翻译成各分区 ViewModel。这一层是纯函数式的，被 231 个测试文件大量直接测试。
▲ 只消费场景状态
④ UI 层 · UI/ 58 文件 + App/ 16 文件
StatusBarController（菜单栏壳）、StatusPopoverView（SwiftUI 弹层内容）、Settings/（设置中心 23 文件）、Icon/（渲染器与缓存 17 文件）；App/ 放生命周期类（激活策略、Dock 点击行为、登录项、单实例、更新、充电效果监控、同步器×2）。

另有三个横向模块：Audio/（20 文件，CoreAudio/ DDC 封装）、Localization/、Telemetry/（9 文件）。

核心数据流：事件驱动 + 兜底轮询

系统事件源（推送）＋ 兜底轮询（默认 15s）→ 各 Monitor→ SystemStatusStore→ @Published snapshot→ IconPresentationViewModel→ 场景状态→ 渲染器（菜单栏/Dock）

SystemStatusStore 顶部注释把能效策略写得非常清楚（这是全项目最值得抄的一段设计）：

  • 推送优先：电池走 IOKit 通知、Wi-Fi 走 CoreWLAN 事件、音量走 CoreAudio 属性监听、网络走 NWPathMonitor——每个变化都有推送通道；
  • 兜底轮询：电池每 tick 都刷新（它画在图标上，不能陈旧）；Wi-Fi 与音量只在弹层和设置窗都不可见时，每第 4 个 tick刷一次（hiddenFallbackTickStride = 4，防推送丢失的看门狗，默认间隔下即 60 秒一次）；
  • 睡眠感知：显示器睡眠时跳过轮询，但最多连跳 20 次（maximumDisplayAsleepSkips，防"唤醒通知丢失导致电池读数冻结一整个会话"的自愈上限）；
  • 定时器宽容：休眠容忍度为间隔的 1/5（refreshSleepTolerance）——不要求 CPU 精确唤醒，常驻菜单栏 App 的礼貌；
  • 弹层防抖：弹层数据 500ms 合并（popupDebounceInterval），避免打开瞬间十几个信号连续重绘。
📌 旁路状态刻意不进快照：VPN 状态、受限网络标记、弹层可见性等都单独 @Published，注释明确说明理由——"没有任何东西画它，就不该进入快照的相等性比较路径"。这保证了图标渲染缓存 key 的最小化。

StatusSnapshot：一个值类型统治图标

StatusSnapshot          // 电池 + Wi-Fi/连接 + 音量 的当前值（Equatable）
  ├─ battery:    百分比/充电/低电量模式…
  ├─ connection: NetworkConnection（wifi/热点/临时/共享/有线/离线…）
  └─ volume:     等级/静音/设备…

快照相等性 = 图标不变 = 不重绘

整套 UI 都从这个值类型的变更驱动：SwiftUI 视图订阅 store.$snapshot，图标管线订阅经 removeDuplicates() 过滤后的同一流（Combine）。设置变更则走 settings.iconPresentationPublisher 另一条流，两流在 IconPresentationViewModel 合并。

  • 120×120 原始几何坐标系按比例缩放到目标 pt，矢量结构源自仓库里的 status-menubar.svg；
  • SF Symbols 墨水居中补偿：符号布局框 ≠ 可见墨水，渲染器按配置缓存每个符号的轴承补偿（Issue #30 的核心教训，两条回归测试永久看护）；
  • 菜单栏/Dock 对等原则：AGENTS.md 规定任何图标改动必须同 PR 镜像到 Dock 渲染（含设置项、缓存 key、订阅、测试五处），菜单栏专属设置必须文档化并有测试声明；
  • 充电动画独立成 时间线系统（Event → Timeline → Phase → Palette → 帧缓存），尊重 Reduce Motion 与显示器睡眠，带测试模式。

蓝牙电量：三源合并 + 可见性门控

来源机制定位
① IOBluetooth 配对报告系统接口直接带电量主要来源
② pmset 配件电源 + AccessoryPowerNotify 事件PmsetAccessoryBatteryWorker + 事件监听补 ① 缺失的设备
③ CoreBluetooth LE 扫描GATT Battery Service 广播解析（BluetoothLEBatteryParsing）附近未配对设备；默认关；允许列表；仅授权且弹层可见时才创建 CBCentralManager；会话取消门控 + 候选缓存 + 合并去重

连接/断开走 IOBluetoothConnectionEventMonitor + BluetoothDeviceActionPerformer（HID 类设备行内二次确认）。两个"同步器"（BluetoothAudioIconOverrideSynchronizer / BluetoothNearbyBatteryOptOutSynchronizer）专职把系统状态与设置偏好协调成最终图标/面板行为，避免把这类胶水逻辑撒进控制器。

设置系统与响应式联动

UserDefaults ←→ SettingsStore（1333 行，60 个 @Published，didSet 即持久化）
                    │
                    ├→ store.bindInputSettings(settings)        // 轮询间隔、输入开关…
                    ├→ store.bindMobileBatterySettings(...)     // Apple 设备刷新策略
                    ├→ IconPresentationSettings(...)            // 外观 → 图标管线
                    ├→ StatusBarController(isVisible:)          // 位置开关
                    └→ 设置界面双向绑定
  • 设置键有强类型默认值与取值范围（如图标大小 iconSizeRange、电池阈值范围）；
  • 跨版本迁移独立成文件（AppleDeviceSettingsMigration），不污染主 Store；
  • 设置的每次订阅都 removeDuplicates()，防止 UserDefaults 回写触发回环刷新。

遥测与生命周期

  • 遥测分层：Consent（同意状态与版本）→ Eligibility（生产/调试资格）→ AppMetadata（快照内容）→ Models → Transport（URLSession）→ Client（发送）→ Reporter（编排）；接口化 TelemetryReporting 便于测试与关闭；
  • 生命周期对称：AppEnvironment.start()/stop() 成对（telemetry 停、时钟停、订阅清空、observer 移除）；通知观察者用 SystemEventObserverBag 聚合注销，避免泄漏；
  • teardown 安全：nonisolated(unsafe) 仅用于"仅主 Actor 写、任意线程可注销"的 observer 句柄，注释里逐条论证安全性（Swift 6 deinit 隔离限制下的标准姿势）。

可复用的架构经验（复刻清单）

  1. 组合根集中装配：main 极薄，AppDelegate 只管生命周期，一切依赖在 AppEnvironment.live() 可读地串起来——测试想换哪个监控器就换哪个；
  2. 监控器协议化：any BatteryMonitoring 这类抽象让 5.5 万行测试代码可以完全不碰真实系统 API；
  3. 单一快照 + 刻意的旁路：能画进图标的进快照，只服务面板的走独立属性——渲染缓存 key 因此天然最小；
  4. 纯函数映射层：状态→场景的翻译不碰系统，逻辑测试不需要起 App；
  5. 能效常量集中且带注释故事：步长、跳过上限、容忍度全部具名常量并解释推导过程，一年后仍可安全修改；
  6. 菜单栏/Dock 同源渲染：一套场景状态喂两个渲染器 + 各自缓存，从第一天保证双端一致（否则永远在补票）；
  7. 把"容易静默坏"的东西写成契约测试：SDK 版本、appcast 语言覆盖、私有 API 链接、居中几何——脚本断言，不靠人眼。
